## 1. Plan (written before building)

Intent: make the database itself enforce doc 06, and make every enforcement provable by a test that talks to a real PostgreSQL 16.

1. Read doc 06, 05, 04 §6, 11 and the T2 report; list every table, constraint and index, and every place the doc is silent or contradicts itself (section 4).
2. `prisma/schema.prisma` at the repo root (architecture §2) for everything Prisma can express; generate the SQL with `prisma migrate diff --from-empty`; hand-write the rest (citext, CHECKs, partial unique index, generated search column, append-only trigger) in the same first migration.
3. One `db` module in `apps/api/src/db` that owns the Prisma client; `/ready` gets its check from it (`SELECT 1`), still injected into `createApp`.
4. Test harness: per run, one migrated template database built with the real `prisma migrate deploy`; per test file, a copy of it; truncate between tests. Constraint tests use plain `pg` so they assert on PostgreSQL's own SQLSTATE and constraint name.
5. Seed as a tested function (`seedDatabase`) plus a thin CLI.
6. CI: migrate deploy → status + drift check → tests → build → seed twice. Smoke: migrate + seed before start, and a second proof that `/ready` is real (an instance with an unusable database must answer 503).

## 3. Notable decisions (alternatives rejected and why)

| Decision | Chosen | Rejected, and why |
|---|---|---|
| Prisma version | **7.10.1** | The registry's `latest` tag points at `8.0.0-rc.33`, a release candidate. 7.10.1 is the newest stable. Consequence: Prisma 7 has no Rust query engine; the client is generated TypeScript and needs a driver adapter (`@prisma/adapter-pg` + `pg`). |
| Schema location | `prisma/` at the repo root, config in `prisma.config.mjs` | Inside `apps/api`: simpler module resolution, but contradicts architecture §2. `.mjs` rather than `.ts` because a root-level `.ts` file belongs to no tsconfig and the type-aware ESLint setup rejects it. |
| Generated client | `apps/api/src/generated/prisma`, git-ignored, regenerated by the root scripts | Committing generated code (noise, drift). A `postinstall` hook (hides a step; a schema edit without reinstall leaves a stale client). |
| IDs | `uuid` with `DEFAULT gen_random_uuid()` in the database | ULIDs generated in the application: sortable, but every raw-SQL insert (seed, jobs, tests) would need the app to mint IDs. Doc 06 allows either. |
| Enumerations | Native PostgreSQL enums | `text` + CHECK: easier to extend, but no type in the client. Cost: a new value needs a migration (`ALTER TYPE … ADD VALUE`). |
| Test isolation | A **database** per test file, copied from a per-run migrated template | A schema per suite (the task text allows either): `citext` is installed into one schema, so a second schema in the same database cannot see the type without search-path tricks. Truncate-only in one shared database: test files run in parallel. Transactions rolled back per test: cannot test code that manages its own transactions (T15). |
| Constraint tests | Plain `pg`, asserting SQLSTATE + constraint name | Through the Prisma client only: would prove the client rejects, not the database, and its error text is less precise. A few tests additionally show what the client surfaces (`P2002`, error message containing the constraint name). |
| Append-only guard | `BEFORE UPDATE OR DELETE` row trigger + `BEFORE TRUNCATE` statement trigger, with a transaction-local opt-in `akiba.event_maintenance` (`purge` → DELETE/TRUNCATE; `merge` → UPDATE of `title_id`/`entry_id`/`run_id` only) | *Revoking UPDATE/DELETE from the application role* (doc 11 says "DB permission test"): needs a two-role setup (owner vs app) that no environment has yet; worth revisiting at deployment (open question 3). *Letting the user cascade bypass the guard*: a row trigger cannot tell a cascade from a direct delete reliably, and an unguarded cascade would make `DELETE FROM "user"` a one-statement way to destroy history. So purge must opt in explicitly. `merge` was added because doc 05 §5 requires the merge script to repoint `event`; without it T9 would need a migration to loosen the trigger. |
| `event` foreign keys | `user_id`, `entry_id`, `run_id` → CASCADE; `title_id` → RESTRICT | `entry_id` NO ACTION/RESTRICT: then the user-purge cascade depends on the order in which PostgreSQL fires the cascades. `run_id` SET NULL: that is an UPDATE on `event`, which the guard forbids. With CASCADE everywhere, the trigger is the single gate: deleting an entry or run that has events fails unless in purge mode (tested). |
| Search column | `title.search tsvector GENERATED ALWAYS AS (title_search_vector(…)) STORED` + GIN, `'simple'` configuration, weights A (romaji, English), B (native), C (synonyms) | A trigger-maintained column (more moving parts). An expression index only (the query must repeat the expression exactly). `'english'` configuration: stems and drops stop words, wrong for names in mixed languages. Limitation: Japanese text is not segmented, so native titles match only as whole tokens. |
| Seed location | `apps/api/src/db/seed.ts` (compiled, linted, tested), run via `pnpm db:seed` / `prisma db seed` | `prisma/seed.ts` as architecture §2 sketches: it would sit outside every tsconfig and need a TS runner (`tsx`) as a new dependency. |
| `/ready` semantics | `SELECT 1` only | Also checking `_prisma_migrations`: couples readiness to Prisma's bookkeeping and would 503 a healthy old version during a rolling deploy. |

## 4. Doc ambiguities and the choice made (each is a deviation or interpretation)

1. **`status = removed` vs `removed_at`** (doc 06 §3 mentions both; §2 lists neither). Chosen: nullable `library_entry.removed_at`; the status enum stays the five documented values.
2. **Unique `(user_id, title_id)` vs tombstones.** The unique constraint covers removed entries too. Consequence for T15: re-adding a removed title must *revive* the tombstone (clear `removed_at`), not insert a second row. Tested ("still rejects a duplicate when the first entry was soft-removed").
3. **FR-TRK-007 "DB check where total is stored on the entry".** Implemented as `progress <= episodes_total_override` when an override is set. Consequence for T16: lowering an override below current progress fails at the database unless the service lowers progress in the same statement. The bound against `title.episodes_total` cannot be a CHECK and is left to the service (a test documents that the DB accepts it).
4. **`title.kind` vs `title.format`**: both are listed. `kind` is the normalised enum; `format` is nullable free text for the source's own label.
5. **`airing_episode.source`, `mapping_conflict.source_a/b`, `mapping_override.source`** use the `anilist|mal|kitsu` enum. The adapter is called `jikan` but serves MAL IDs, so Jikan data is recorded as `mal`.
6. **`title_character.role`**: enum `main|supporting|background` (doc gives no values).
7. **`title.season`**: enum `winter|spring|summer|fall` (doc gives no values).
8. **`title.start_date`/`end_date`** are `date`. Partial source dates (year only) cannot be stored; the adapter must decide (open question 5).
9. **Title names** are all nullable with a CHECK that at least one is present (sources do not guarantee romaji).
10. **Nullable/default choices not in the doc:** `user.display_name` nullable; `time_zone` default `'UTC'`; `title_language` default `romaji`; `library_view` default `grid`; `alerts_enabled` default `true`; `title.synonyms` default `{}`; `studio.is_animation_studio` default `true`; jsonb `external_ids` default `{}`; `event.payload` default `{}`; `event.occurred_at` default `now()`; `viewing_run.progress_at_end` nullable (unknown while the run is open).
11. **Cascade rules** (doc 06 gives none): see `prisma/README.md` "Foreign-key rules". Notably `mapping_override.title_id` is RESTRICT (a manual decision should not vanish with a title).
12. **Events and hard deletes.** Doc 06 §3: "never updated or deleted (except by account purge)". Implemented literally, plus the `merge` exception from doc 05 §5.
13. **Timestamps** are `timestamptz(3)` (millisecond precision, what JavaScript dates carry).

## 6. Deviations from the docs / brief

- Section 4 items (interpretations where the doc is silent or inconsistent).
- Seed lives in `apps/api/src/db/`, not in `prisma/` (architecture §2 says "schema.prisma + migrations + seed").
- Requirement IDs: the brief suggested FR-REM-007 for "one open run". In the SRS, FR-REM-007 is "Events shall be append-only" and rewatch runs are FR-REM-004, so the run tests are named FR-REM-004 and the event tests FR-REM-007.
- The two T2 tests of the TCP probe (`createTcpDbCheck`) were removed together with the probe. They are replaced by stronger tests of the same guarantees against a real server (ok when reachable; rejects when nothing listens, on a wrong password and on a missing database; the password never appears in logs or responses). The `dbNotConfigured` test was kept.
- `pnpm test` now fails fast without a PostgreSQL (`DATABASE_URL`/`TEST_DATABASE_URL`), with a message saying what to set. Before T3 the API tests needed no database.
- Doc 11 names Testcontainers/Docker for the disposable database; the harness uses whatever server `DATABASE_URL` points at (the CI service container; a local `initdb` cluster here, because Docker is not available in this environment).
- Seed data is hand-written sample data about real titles (names, episode counts, dates, AniList/MAL IDs written from memory, **not fetched or verified**), flagged `stale = true` so the first metadata refresh overwrites it. Synopses are one-line placeholders.

## 9. What I did NOT run / could not verify

- **Seed data accuracy**: not checked against AniList or MAL (no live calls; none wanted in CI either).
- **A non-superuser database role.** Local and CI roles are superusers. `CREATE EXTENSION citext` should work for a plain database owner on PostgreSQL ≥ 13 (trusted extension), and the tests need `CREATEDB`; neither was tried with a restricted role, nor on a managed PostgreSQL.
- **PostgreSQL 15**, which doc 06 allows ("≥ 15"). Only 16 was used.
- **Concurrency**: no test inserts two open runs or two duplicate entries from concurrent transactions. Unique indexes are atomic in PostgreSQL, so this is expected to hold, but it is not demonstrated.
- **Query plans / performance** of the indexes (doc 11 "EXPLAIN checks"): only their definitions are asserted.
- **A second migration** on top of the first (the "Writing the next migration" steps in `prisma/README.md` were derived from how the first was produced, not exercised end to end).
- **`prisma db seed`** via the Prisma CLI; only `node apps/api/dist/db/seedCli.js` and the `seedDatabase` function were run.
- **Rollback/down migrations**: Prisma has none; not addressed.
- **Coverage measurement**, shellcheck on the new smoke file (not installed; `bash -n` only).
- **`pnpm db:check` cannot detect a missing CHECK, partial index, function or trigger** (Prisma's diff ignores them). They are covered by behaviour tests only.
- Prisma's `$disconnect` does not make a handle unusable: a later query reconnects. `close()` is therefore "release connections", verified through `pg_stat_activity`, not "poison the handle".

## 10. Open questions for the coordinator

1. **Tombstone + unique `(user_id, title_id)`**: is "re-add revives the removed entry" the intended behaviour for T15? The alternative (a partial unique index on live rows) allows several tombstones per title and splits a title's history across entries.
2. **Override lower than progress** is rejected by the database. Should T16 clamp progress when the user lowers an override, or refuse the change?
3. **Append-only by trigger vs by privilege.** The trigger stops bugs, not a role with SQL access. When deployment is decided (D-24), consider a separate application role without UPDATE/DELETE on `event`, which is what doc 11's "DB permission test" seems to mean.
4. **Adult-content preference**: T19 mentions a user toggle (Q-10) but doc 06 has no column. Add `user.show_adult` in the task that needs it?
5. **Partial dates** (year-only start dates from sources) do not fit `date` columns. Acceptable to store null, or should doc 06 get separate year/month/day columns?
6. **The registry's `latest` Prisma tag is a release candidate (8.0.0-rc).** I pinned 7.10.1. Revisit when 8.0 is stable.
7. `pnpm test` now requires PostgreSQL locally. If that is too strict for contributors working only on `packages/*` or `apps/web`, the alternative is to filter (`pnpm --filter @akiba/web test`), which already works.
8. Doc 06 §2 could be updated with the columns and choices in section 4 (I did not edit the docs).
